There are two ways to improve a language agent: update its model weights, or change its **harness**—the code that decides what the model sees, what it keeps track of, and how it interacts with the environment. If both can change, what's the right way to train them? Should we improve one at a time, or let both learn from the same task attempt?

Our answer with **JoMoHa**: train both from the same attempt, but give each a learning signal that accounts for how it worked with the other.

[Read the paper](https://arxiv.org/abs/2611.11499) · [Explore the code](https://github.com/xudongwu-0/coevolve)

## Why not optimize one at a time?

The simplest recipe is to freeze the harness while updating the model weights, then freeze the model while training a policy to generate better harnesses. The catch: each side learns to work with a partner that changes in the next phase. In our long-phase alternating run on ALFWorld, success initially rose from **83.0% to 90.5%**, then fell to **31.5%**.

One failed task made the mismatch easy to see. The sponge was already clean; all the agent had to do was put it on a cart. But the harness missed the state update and kept sending the agent back to clean it. The model hit the **50-turn limit**. Without the harness, the same model finished in **14 turns**.

That wasn't the only problem. Across tasks, the later model performed worse than the earlier checkpoint even after we removed the learned harness. So the decline wasn't just a runtime bug: the harness also shapes the experience the model learns from. Swapping out a bad harness at test time doesn't undo what the model learned under it.

## How do we train both from one attempt?

In JoMoHa, an **Engineer** writes an executable harness and a **Solver** uses it to act. We train both policies with reinforcement learning from the **same task attempt**: the Engineer learns to write a better harness for the Solver it actually worked with, and the Solver learns from acting under that harness. The system learns to write its own harness rather than relying on a fixed external editor.

### Same reward, different expectations

Go back to the sponge. A failed run tells us the pair didn't finish, but not whether the harness misread the state, the Solver made a bad decision, or the two simply worked poorly together. A shared reward tells both policies *what happened*. It doesn't tell either policy *what to expect* under those conditions.

That's where the two **critics** come in. Each estimates a baseline for its own policy: the Engineer's critic judges the outcome in light of the Solver it's writing for; the Solver's critic judges it in light of the harness it's working under. The critics stay separate, but each gets a short summary of the collaboration, including the task, training version, and execution conditions. Only the critics see this extra context, and only during training.

That gives each policy a more useful question than “Did we win?”: **“Did we do better or worse than expected with this setup?”** JoMoHa also normalizes returns separately for each role, weights policy updates using the partner's recorded trajectory, and gives the Solver extra rounds to adapt to new harnesses.

## Does coordination matter beyond joint training?

On ALFWorld, training both policies from the same runs without the coordination mechanisms reached **88.5%**. Adding critic context alone raised that to **92.5%**, the largest gain among the individual additions. Combining all four mechanisms reached **97.0%**. A separate control that kept the Engineer frozen while still sampling fresh harnesses reached **90.5%** at the same reported training step.

JoMoHa led the methods we compared on all three benchmarks: **97.0%** on ALFWorld, **45.8%** on WebShop, and **68.0%** on DBBench. That's **70.3% average task success**, **7.2 percentage points above WHALE**.

When both the weights and the harness can change, **use the same task attempt to train both, and judge each update in the context of how they worked together.**
